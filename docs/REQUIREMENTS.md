# uom: Requirements

Status: reviewed by the project owner. The design is in `DESIGN.md`. Milestones 1 to 5 are
implemented on their branches (units core, `double` and `BigDecimal` quantities for all 33 types, the generator, the
seven catalogs, `quantity.to(system)`, basic formats, the service provider, the TCK passing); the rest is not.

## 1. Purpose

A general-purpose, published open-source Java library for quantities and units of measurement,
restarted from the unfinished `netomi/uom`. It targets the `javax.measure` (JSR-385) API and
differs from existing implementations (e.g. Indriya) in two ways:

1. **Fully typed quantities.** `Length`, `Mass`, `Speed`, ... are real classes that implement the
   standard interfaces, not just `Quantity<Length>` instances of one generic class.
2. **Multiple unit systems** with conversion between them, as a first-class feature.

Success means a developer can use uom wherever JSR-385 code is expected, gets typed values
and catalogs for SI, Imperial/US customary and CGS units, and has no runtime reflection or
dynamic proxies in the picture.

## 2. Scope

### In scope for 1.0

| ID | Requirement |
|----|-------------|
| F1 | Implement the JSR-385 API (`javax.measure`): `Quantity`, `Unit`, `UnitConverter`, `Dimension`, `SystemOfUnits`, service provider. Target version: `javax.measure:unit-api` 2.2 (latest, May 2023; 15 methods on `Quantity`, 25 on `Unit`). Older versions are not supported. |
| F2 | Own implementation of the units side: no dependency on Indriya or any other JSR-385 implementation at runtime. |
| F3 | Typed quantity classes are generated by an internal code generator from data files, and the generated sources are committed. No proxies, no runtime reflection for quantity creation, no annotation processing for consumers. |
| F4 | Generated quantities implement the standard quantity interfaces (`javax.measure.quantity.Length`, ...) for the built-in set of quantity types (those in unit-api, plus any further types the catalogs need). A typed quantity is accepted anywhere `Quantity<Q>` is. |
| F5 | Two numeric precisions from the first release: `double` and `BigDecimal`. Both are generated for every quantity type (done in milestone 4: `XDouble` and `XDecimal` for all 33 types). Mixing precisions in one operation has a single, documented promotion rule (F23). |
| F6 | Unit catalogs (done in milestones 3 and 5: `SI` 128 distinct units, `USCustomary` 35, `Imperial` 42, `CGS` 16, `ESU` 22, `EMU` 29, `Gaussian` 26; poise, stokes and oersted are untyped units): SI (all prefixes, plus accepted non-SI units such as minute, hour, litre, tonne, electronvolt), Imperial / US customary (US and imperial gallons distinguished, international vs US survey foot distinguished), CGS mechanical, and CGS electromagnetic (ESU, EMU, Gaussian). |
| F7 | CGS electromagnetic units are conversion conventions: a statcoulomb is a unit of `ElectricCharge` with a numeric factor to the coulomb. They are not modelled as separate dimension sets. |
| F8 | Typed system conversion (done in milestones 3 and 5: `UomSystemOfUnits` implements `SystemOfUnits` with preferred units for all 33 types in every system; `quantity.to(system)` on every typed quantity): `quantity.to(system)` converts to the system's preferred unit for that quantity type (e.g. CGS gives centimetre for a length). A unit system maps quantity types to their preferred unit. |
| F9 | Basic formats done in milestone 3 (`UomUnitFormat`, `UomQuantityFormat`: symbols, prefixes, formulas such as `kg·m/s^2`); locale-aware formats are milestone 6. Unit parsing and formatting (e.g. `"km/h"`, `"m/s^2"`), and quantity formatting (value plus unit symbol). |
| F10 | Unit algebra per JSR-385: multiply, divide, pow, root, prefixes, shift (offset units such as degree Celsius and Fahrenheit), transform, alternate units, and base-unit decomposition. |
| F11 | Compatibility checking: combining incompatible units fails with a clear unchecked exception naming both units. |
| F12 | Quantities and units are immutable, thread-safe and `Serializable`. |
| F13 | A `module-info.java` (JPMS) for every published module. |
| F14 | ~~User-defined quantity types~~ Moved out of scope for 1.0 (see below). |
| F15 | **Unit definitions live in text data files**, which are the single source of truth for the catalogs (F6). The file syntax is a design decision. The original uom `.units` format (GNU units style: `symbol:name formula`, `@include`, `!` base units, `~` alternate units, `a|b` fractions, affine functions) is a starting point, not a constraint. The syntax must express: symbol and name, a formula over other units, exact rational and decimal factors, offsets and affine functions, base units, alternate units, includes, comments, and (F16) an optional explicit quantity type. |
| F16 | **Typed catalog constants are generated from the data files** (e.g. `Unit<Length> INCH`, `Unit<Energy> JOULE`). The quantity type of a unit is inferred from its dimension, and may be stated explicitly in the definition where the dimension is ambiguous (e.g. energy and torque; hertz and becquerel; gray and sievert). An ambiguous definition with no explicit type is a build error. |
| F17 | Status after milestone 3: the generator and the formula evaluator share one parser, but `.units` resources are not loaded at run time; `UomUnitFormat` resolves symbols from the generated catalog. **The same definitions drive the unit parser (F9)**, so a symbol such as `"ft"` resolves to the same unit in code and in text. Whether definitions are processed at build time, at run time, or both is a design decision. |
| F18 | Status after milestone 3: not implemented; the generator reads `data/` only. **Users can supply their own `.units` files** (extending or including the built-in ones), processed by the same generator. They can define units of the built-in quantity types only. |
| F19 | **Definition errors are build errors with file and line:** unknown unit, duplicate symbol, circular definition, dimension mismatch, unparsable formula. |
| F20 | **Quantity equality.** `isEquivalentTo` follows the standard: same numerical value after conversion to the same unit, ignoring rounding errors (2 km is equivalent to 2000 m; 2 °C is equivalent to 275.15 K, not to 2 K). `equals` and `hashCode` are strict and mutually consistent: same implementation class, same unit, same scale and same value (`Double.compare` semantics for double, `compareTo == 0` for BigDecimal, so `1.0 m` equals `1.00 m`; the `MathContext` is not part of equality; settled in milestone 4). `isEquivalentTo` uses a relative tolerance of 1e-12 for `double` (asymmetric near zero for offset units, no absolute floor); for `BigDecimal` the tolerance is `10^(1-p)` relative, where `p` is the lowest non-zero precision of the two `MathContext`s (34 when both are unlimited), also with no absolute floor; against a `double` operand the `double` tolerance applies (settled in milestone 4). `equals` is deliberately not `isEquivalentTo`, because a tolerance cannot satisfy the `equals` contract. |
| F21 | **Unit equality.** `Unit.equals` follows the examples in the standard: `getSystemUnit().equals(...)` must identify a quantity type, and alternate units differ from the unit they are derived from (`RADIAN.equals(ONE)` is false although they are compatible). Equality is structural over the system-unit decomposition and the converter, not over symbol or name. `isEquivalentTo` on units means the converter between them is the identity. |
| F22 | **`Comparable`.** Quantities implement `Comparable<Quantity<Q>>`, because the unit-api 2.2 `Quantity` Javadoc says all implementations must be `Comparable`. Ordering is by system-unit value with `Double.compare` semantics (for `double`) and is not consistent with `equals`. |
| F23 | Status: implemented in milestone 4 (`AbstractDecimalQuantity`, `AbstractDoubleQuantity`, `Precision`). **Precision rule: the lower precision wins.** Mixing is allowed. When two quantities of different precision are combined (add, subtract, multiply, divide, `isEquivalentTo`), the result has the lower precision, because a result cannot be more precise than its least precise input. The rule is symmetric, so `a.add(b)` and `b.add(a)` have the same result type. Specifics: (1) `double` ranks below any `BigDecimal`; between two `BigDecimal` quantities the smaller `MathContext` precision wins (0, unlimited, is highest); a coarse `BigDecimal` is not demoted to `double`. (2) Scalar `Number` arguments (`multiply(Number)`, `divide(Number)`) are exact constants and adopt the receiver's precision. (3) Demoting a `BigDecimal` outside the `double` range throws `ArithmeticException`, never `Infinity`. (4) Every `BigDecimal` quantity carries a `MathContext` (default `DECIMAL128`) that rounds every computed result (conversions and arithmetic; `DECIMAL32` `1.23456789 + 0` gives `1.234568`); creating a quantity does not round its value. `UNLIMITED` keeps results exact where they terminate and falls back to `DECIMAL128` otherwise. (5) Explicit conversions are always available (`toDouble()`, `toDecimal(MathContext)`). For `add`, `subtract` and the scalar operations the result unit is the left operand's unit; quantity-by-quantity `multiply`/`divide` and `inverse` return untyped results in system units (D7). A strict no-mixing mode is not provided. |
| F24 | **Arithmetic follows the `Quantity` Javadoc literally.** `add`, `subtract`, `multiply(Number)` and `divide(Number)` behave as if all operands were converted to the system unit first and the result converted back to the unit of the left operand, with a fast path for linear units. For offset units `2 degC + 1 degC` is 276.15 degC and `2 degC - 1 degC` is -272.15 degC. `negate` is the literal negation of the value in the same unit. The Javadoc's own example "2 degC + 1 degC = 274.15 degC" contradicts its rule (the rule gives 276.15 degC); this is recorded for the TCK work. |

### Explicitly out of scope for 1.0

- User-defined quantity types. The quantity types are the built-in set. Users can still add
  units of those types (F18).
- Typed quantity products and quotients (`Length / Time` returning `Speed`, `Length * Length`
  returning `Area`). JSR-385 `multiply` and `divide` return `Quantity<?>`; narrowing is by
  `asType(Class)`. Declared relations can be added in a later release.
- Modelling ESU/EMU/Gaussian as distinct dimension systems (option B in the design notes).
- Arbitrary-precision support for transcendental conversions beyond what `BigDecimal` and
  `MathContext` give.
- Database, JSON and framework integrations.
- Android or Java versions below the baseline.

## 3. Constraints

- Build with Maven. Multi-module.
- Java baseline 21 (the unit-api 2.2 dependency itself targets Java 8, which is compatible).
- License Apache-2.0 (already in the repository).
- No dynamic proxies. The library works on the class path and the module path on JDK 21 through
  the current JDK. Consumers need no annotation processing.
- The code generator is an internal developer tool that emits plain Java source; a
  code-generation library dependency is allowed only if it earns its weight.
- Runtime dependencies: only the JSR-385 API artifact. The code generator is not published.

## 4. Non-functional requirements

| ID | Requirement |
|----|-------------|
| N1 | **Conformance:** pass the JSR-385 compatibility tests (`tech.units:unit-tck` 2.2) for the implemented API. If the TCK cannot be run against a non-Indriya implementation, write an equivalent contract test suite. |
| N2 | **Correctness:** unit conversions use exact definitions where the definition is exact (inch = 0.0254 m, c = 299 792 458 m/s). Factors are expressed as exact rationals or `BigDecimal` in the catalog source and rounded once for `double`. |
| N3 | **Performance:** `double` quantity operations allocate at most the result object; no reflection, boxing or map lookups on the hot path. Converters between two units are cached or precomputed. |
| N4 | **Compile-time safety:** adding quantities of different types, or passing a unit of the wrong quantity to a typed factory, is a compile error wherever the standard API allows it. Where the API forces a looser parameter type (`Quantity<Length>` rather than `Length`), return types stay typed. |
| N5 | **Diagnostics:** the generator and the parser report data-file errors with file and line (F19). |
| N6 | **Testing:** unit tests per module, golden tests for the generator (sample inputs compile, behave, and report errors with file and line), and a property-style round-trip test over every catalog unit (convert to the system unit and back within tolerance). |
| N7 | **Documentation:** README with a five-minute example, a guide for adding custom units, and a table of catalog units with their systems. |
| N8 | **Release:** versioned releases on Maven Central as `org.tinygears:uom-*`, semantic versioning, a public API definition (what is stable) in the docs. |

## 7. Risks

- **Scope.** Own implementation of the whole unit API plus two precisions plus four unit
  systems is a large project. Mitigation: staged milestones (core and double first, then
  BigDecimal, then catalogs) with each stage releasable.
- **TCK portability.** The TCK's POM references Indriya and TestNG; it may assume the reference
  implementation. Mitigation: spike early; fall back to our own contract tests (N1).
- **API friction.** The standard fixes parameter types such as `Quantity<Length>`, so
  generated types cannot be stricter than the standard on inputs.
- **Generated code volume.** Two precisions per quantity type multiplies generated classes.
  Mitigation: keep generated classes thin and push shared logic into non-generated base
  classes.
- **Definition data licensing.** GNU units' data file is GPL. The `.units` files must be
  authored independently (from SI, NIST and CODATA definitions) and cross-checked against
  reference values, never copied from GNU units, so the library stays Apache-2.0.
- **Dimension ambiguity.** A formula determines a dimension, not a quantity type. Units such as
  hertz/becquerel and gray/sievert need explicit typing (F16).
- **Electromagnetic CGS semantics.** Treating ESU/EMU/Gaussian as conversion factors converts
  values but not formulas; the documentation must say so.

## 8. Acceptance criteria for 1.0

1. A user obtains typed `double` and `BigDecimal` quantities for all built-in quantity types
   without writing any implementation, and can add units by loading their own `.units` files.
2. Typed quantities from uom are accepted by generic JSR-385 code, and the conformance
   tests (N1) pass.
3. All four unit systems in F6 are available as catalogs, with the round-trip test (N6)
   passing for every unit.
4. Units can be parsed from and formatted to their symbols, and quantities are formatted.
5. Quantities and units survive Java serialization round trips.
6. The library works on the module path and on the class path, on JDK 21 and the current JDK.
7. Artifacts are published to Maven Central with the documentation from N7.
