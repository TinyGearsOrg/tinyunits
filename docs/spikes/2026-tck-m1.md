# TCK spike, milestone 1

Question: can the JSR-385 TCK (`tech.units:unit-tck:2.2`) run against uom instead of
Indriya, and what must milestone 3 provide? Short answer: yes. The TCK has no code
dependency on Indriya and runs against `uom-core` today. All unit, dimension, converter and
prefix tests pass; the failures are all missing quantities, services and formats. The TCK
only checks that methods exist, though, so it says almost nothing about behaviour.

## Setup

- Spike branch `spike/tck` (worktree `../tinyunits-spike`), last commit `bdf510a`
  "test: run the JSR-385 TCK 2.2 against uom-core (spike, not for merge)". Never merged
  or pushed.
- Scratch module `uom-tck-spike` (added to the parent `<modules>` on that branch only),
  test dependencies `tech.units:unit-tck:2.2` and `org.testng:testng:7.8.0` (the version
  the TCK POM pins), plus `uom-core`.
- Surefire 3.2.5 runs the TCK classes from the jar via
  `<dependenciesToScan>tech.units:unit-tck</dependenciesToScan>`. The parent's
  `junit-jupiter` makes surefire auto-select the JUnit Platform provider, which finds 0
  tests. The module therefore declares `surefire-testng:3.2.5` as a plugin dependency.
  Class path, not module path (parent sets `useModulePath=false`). JDK 25, Maven 3.9.16.
- `UomTckConfiguration` implements `tech.units.tck.util.ServiceConfiguration`
  (registered in `META-INF/services`). Unit classes: `UomUnit`. Dimension classes:
  `UomDimension`. Quantity classes: none. Converters: identity, scale 1000, shift 273.
  Units under test: the 7 base units, `ONE`, km, a shifted kelvin, m/s. Base dimensions:
  the 7 SI ones. Formats: none. `getUnit4Type` maps the 7 base quantity types and
  `Dimensionless` to `BaseUnits`.
- `StubServiceProvider` extends `javax.measure.spi.ServiceProvider` with every service
  returning `null`.
- Reproduce: `cd ../tinyunits-spike && mvn -q -B -pl uom-tck-spike -am test`, then read
  `uom-tck-spike/target/surefire-reports/testng-results.xml`. Add `-Dgroups=core` for
  the TCK's MINIMAL profile.

### How the TCK finds an implementation

- `TCKSetup` loads the first `ServiceConfiguration` through `java.util.ServiceLoader` in
  a static initializer. If there is none, every test fails with
  `ExceptionInInitializerError` ("No valid implementation of ...ServiceConfiguration").
  First run without it: 113 run, 99 failed. The TCK reads no system properties for
  discovery. `tech.units.tck.profile` etc. are only used by `TCKRunner`, not by surefire.
- The SPI tests call `ServiceProvider.current()` and `ServiceProvider.available()`. A
  provider needs `getSystemOfUnitsService`, `getFormatService` and
  `getQuantityFactory` (the three abstract methods). Without a registered provider,
  `current()` throws `IllegalStateException`.
- Groups: `core`, `format`, `base_quantity`, `derived_quantity`, `spi`. Surefire runs all
  of them unless `-Dgroups` is given, which corresponds to the FULL profile.

### Indriya

The TCK POM declares `tech.units:indriya:2.2` at `test` scope, so it is not transitive.
`mvn -B -pl uom-tck-spike dependency:tree` shows the TCK pulls only `uom-lib-common`,
`jakarta.inject-api`, `slf4j-api`, `jul-to-slf4j`, `hamcrest-library`, `reflections`
(with `javassist`, `jsr305`) and `jboss-test-audit-api`/`-impl` (all `test`). No
Indriya. The TCK sources and jar contain no reference to Indriya outside the embedded
POM.

What a pass means: every unit, converter, dimension, prefix, quantity and format test only
checks, via `TestUtils.testHasPublicMethod`, that the class declares a public method with
a given name, parameter types and return type. It never calls the method. Any class that
compiles against `javax.measure` passes these. With an empty list they pass without
checking anything: all 16 `QuantityInterfaceTest` tests passed with zero quantity
classes, and the format tests other than `testEnsureGot*` passed with zero formats. The
only check that calls `uom-core` is `QuantityTypesTest.testContainsBaseDimensions`
(`getDimension()` of the 7 base units equals the 7 base dimensions).
`ServiceProviderTest` only calls the stub provider. Our method signatures pass because they are covariant
(`UomUnit.divide(Unit)` returns `UomUnit`), and the compiler adds bridge methods that
return `Unit`, so the TCK finds the exact signature it looks for.

## What failed and why

No failure is a defect in `uom-core`, and none is an Indriya-specific assumption. All 28
are missing features:

- Quantities, milestones 2 and 4 (2): `TCKSetupTest.testQuantityConfiguration` and
  `FundamentalTypesTest.testEnsureHasQuantity` require a non-empty `getQuantityClasses()`.
- Formats, milestone 6 (2): `UnitFormatTest.testEnsureGotUnitFormat`,
  `QuantityFormatTest.testEnsureGotQuantityFormat`.
- Service provider services, milestone 3 (24): `ServicesTest` (10), `SystemOfUnitsTest`
  (6), `QuantityFactoryTest` (2), `ObtainingUnitsTest` (2), `ObtainingQuantiesTest` (4).
  These fail on the null `SystemOfUnitsService`, `FormatService` or `QuantityFactory`
  from the stub provider.

What the SPI tests require once the services exist:

- `getQuantityFactory(c)` returns a non-null factory for every `Quantity` subtype that
  `org.reflections` finds under `javax.measure`. That is all 33 interfaces in
  `javax.measure.quantity`, not just the ones in our catalogs.
- `QuantityFactory.create(10d, unit, scale).getScale() == scale` for `ABSOLUTE` and
  `RELATIVE`. The unit comes from
  `getSystemOfUnitsService().getSystemOfUnits().getUnit(Length.class)`.
- At least one `SystemOfUnits`, and a default one. `getPrefixes` must give 24 metric and
  8 binary prefixes; the interface default (enum constants) already does this.
- A `FormatService` with a default `UnitFormat` and `QuantityFormat`. Both
  `getAvailableFormatNames(UNIT_FORMAT)` and `getAvailableFormatNames(QUANTITY_FORMAT)`
  must be non-empty.
- For every unit with a non-null symbol in every available system of units:
  `getUnitFormat().parse(u.toString())` equals `u`, and
  `getQuantityFormat().parse("1 " + u)` has unit `u` and value 1. This round trip is the
  only substantive behavioural check in the TCK.
- `ServiceProvider.available()` tests every registered provider. If Indriya were also on
  the class path, the SPI tests would test it as well.

## Recommendation

Use the TCK with a thin adapter for N1, and also write our own contract tests from the
Javadoc.

- Adapter (milestone 3): a test-scope `ServiceConfiguration` like the spike's (unit,
  dimension, quantity and converter lists, `getUnit4Type` backed by our SI system of
  units, the formats), a TestNG run with an explicit `surefire-testng` provider next to
  JUnit 5, and the real `ServiceProvider` from milestone 3 registered on the class path.
  Indriya stays off the test class path.
- Milestone 3 must provide: quantity classes, a `QuantityFactory` for all 33 API quantity
  types with `Scale` support, a `SystemOfUnitsService` with at least the SI system, a
  `FormatService` with default unit and quantity formats (the format tests need milestone
  6). It must also guarantee that `toString()` of every catalog unit parses back to an
  equal unit.
- Contract tests: the TCK checks that methods exist, not what they do, so passing it is
  necessary for N1 but is no evidence of correctness. The behaviour the Javadoc specifies
  (`getConverterTo` exceptions, `isEquivalentTo`, `getBaseUnits`/`getBaseDimensions` null
  for base items, `inverse`, `concatenate` order, `getSystemUnit`, `asType`) needs our own
  tests, as the risk section of REQUIREMENTS.md anticipates. Much of this is already
  covered by the `uom-core` unit tests. A contract-test suite should gather it per API
  interface.

## Defects fixed

None. The TCK checks almost no behaviour, so the spike exposed no `uom-core` defect, and
this is not evidence that there are none.

## Decisions for the controller

- N1 wording: is "passes the TCK" enough, or does N1 also require our own JSR-385 contract
  tests? The recommendation above assumes both.
- Scope of `QuantityFactory`: the SPI tests require a factory for all 33
  `javax.measure.quantity` types, including any we would not otherwise catalog.
- Unit `toString()` must round-trip through the default `UnitFormat`, so milestone 6
  formatting and the `toString()` labels (`m/s`, `kg·m^2/s^2` from `systemLabel`) must agree.
