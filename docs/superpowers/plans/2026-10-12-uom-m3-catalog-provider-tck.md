# uom Milestone 3: SI Catalog, Provider and TCK Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A published `uom-systems` module with the generated SI catalog of typed units, a `SystemOfUnits` and basic unit and quantity formats, the real JSR-385 `ServiceProvider`, quantity factories for all 33 standard quantity types, and the `unit-tck` 2.2 passing against it.

**Architecture:** The generator reads `data/si.units` (all SI definitions, curated prefixed units) and `data/quantity-types.txt` (33 types), resolves every unit's quantity type from its system unit, and writes the typed catalog class `SI` into `uom-systems` plus the 33 quantity types into `uom-quantities`. Hand-written classes in `uom-systems` provide the `SystemOfUnits`, the formats and the provider; an unpublished `uom-tck` module runs the TCK against them.

**Tech Stack:** Java 21, Maven, JUnit 5.10.2, `javax.measure:unit-api:2.2`; `uom-tck` also uses `tech.units:unit-tck:2.2`, `org.testng:testng:7.8.0` and `maven-surefire-testng` 3.2.5.

**Spec:** `docs/DESIGN.md` (sections 5, 6, 7), `docs/REQUIREMENTS.md`, the spike report `docs/spikes/2026-tck-m1.md`, and the follow-ups `docs/superpowers/plans/2026-10-12-uom-m2-follow-ups.md`. Branch `m3-catalog` is stacked on `m2-quantities` (not merged yet). Spike code to seed the TCK module: branch `spike/tck` (pushed), module `uom-tck-spike`.

## Global Constraints

- Java baseline 21; Maven multi-module; Apache-2.0; every `.java` file starts with `// SPDX-License-Identifier: Apache-2.0` (generated files: that line plus `// Generated by uom-codegen from data/<files>; do not edit.`).
- Group id `org.tinygears`; artifacts `uom-*`; package prefix `org.tinygears.uom`; JPMS modules `org.tinygears.uom.core`, `.quantities`, `.systems` (`provides javax.measure.spi.ServiceProvider`); the provider is also registered in `META-INF/services` (class path and module path both work).
- Runtime dependencies: only `javax.measure:unit-api` 2.2; `uom-codegen` and `uom-tck` are not published. No proxies, no runtime reflection in main code.
- Catalog factors are exact (`Factor`, N2): no `double` literals in generated code except where the definition itself is approximate (the dalton, written as an exact decimal literal).
- Generated sources are committed; the drift test fails on drift; output is deterministic (no timestamps, stable ordering, `\n` endings, `.gitattributes` pins LF).
- Data-file errors carry file and line (F19). Units with an offset can not be multiplied or divided.
- Commit subjects use a conventional prefix (`feat:`, `fix:`, `test:`, `build:`, `docs:`), no emojis. Code comments 1-3 lines.

## Decisions for this milestone

- **D1 Prefixes (confirmed by the owner):** a curated list in the data. `@prefixed <unit> <prefix>...` generates the listed prefixed constants (`km`, `cm`, ...) and also marks the unit prefixable: the unit format resolves any other metric prefix on a prefixable unit at run time (`Gm`, `fs`).
- **D2 Formats now:** the TCK requires a `FormatService` whose unit format parses `toString()` of every catalog unit and a quantity format that parses `"1 " + unit`. A basic working `UnitFormat` and `QuantityFormat` therefore arrive in this milestone; locale handling, more formats and serialization stay in milestone 6.
- **D3 Open owner decisions do not block this milestone** (`docs/TODO.md`): offset-unit arithmetic (D5) and the `asType` rule for alternate units keep their current behavior (literal Javadoc rule; structural system-unit comparison). Nothing in this plan changes either; the TCK checks neither.
- **D4 Types:** 33 standard quantity types (the earlier "34" counted `package-info`). Each has exactly one system unit given in `quantity-types.txt`.
- **D5 Type resolution (F16):** a definition's quantity type is its explicit `[Type]`, else the unique type whose system unit equals the unit's system unit. An explicit type whose system unit differs, or an ambiguous match, is a build error with file and line; no match yields an untyped `UomUnit<?>` constant.
- **D6 Characters:** the micro prefix is `µ` (U+00B5, as `MetricPrefix.MICRO.getSymbol()` returns), the ohm is `Ω` (U+03A9). The multiplication dot `·` (U+00B7) is an operator in formulas, not a symbol character, so unit labels such as `kg·m/s^2` parse back.
- **D7 Provider:** priority 100 so it wins over other JSR-385 providers on the class path.
- **D8 Registry isolation:** `QuantityTypes.factory` resolves each type lazily, so one failing alternate-unit registration cannot take down all types (follow-up from milestone 2).
- **D9 Non-exact definitions:** the dalton is the CODATA 2018 value `1.66053906660e-27 kg` (approximate); every other catalog definition is exact.

## Review Focus

1. **Round trip.** For every catalog unit, `UnitFormat.parse(unit.toString())` equals the unit and `QuantityFormat.parse("1 " + unit)` has that unit; derived labels (`m^2·kg`, `kg/(m·s)`, `(m/s)^2`) parse back; prefix resolution is unambiguous for `dam`, `min`, `mm`, `cd`, `Pa`, `hPa`, `h`, `T` versus `t` (Tasks 1, 9).
2. **Type resolution and validation.** Ambiguous or mismatched `[Type]` is an error with file and line; no two constants share a name; every one of the 33 types has a factory and a preferred SI unit; unresolvable units become untyped constants (Tasks 4, 8).
3. **Global state.** The alternate-unit registry gets the same definitions from the generator, the catalog and the tests (`Hz`, `Bq`, `rad`, `sr`, `Gy`, `Sv`); a conflicting registration affects only its own type; two JVM class loaders are independent (Tasks 3, 8, 10).
4. **Provider and TCK.** `ServiceProvider.current()` is ours even when another provider is on the class path; `getQuantityFactory` for a non-standard `Quantity` subtype fails with the exception the Javadoc names; thread-safety; `provides` works on the module path (Tasks 10, 11).
5. **Exactness.** Generated factors rebuild equal `Factor`s (eV, au, degree with pi, dalton, degree Celsius offset); no `double` literals in generated code (Tasks 6, 8).
