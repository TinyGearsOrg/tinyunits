# uom Milestone 7: Release Engineering and Documentation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Everything needed to publish uom to Maven Central is prepared, tested and documented, and the 1.0 documentation requirements (N7, N8) are met, without publishing anything: complete POM metadata, an inactive `release` profile (sources, javadoc, signing, Central upload), reproducible builds, a documented and tested public API, a generated unit table, a custom-unit guide, a versioning policy, and a CI workflow.

**Architecture:** Release configuration lives in the parent POM behind a `release` profile that nothing activates by default. A script (`scripts/verify-release.sh`) builds the release artifacts, checks them against the Central rules and against a consumer project, and is what the implementers and the CI run. The unit table is generated into `docs/UNITS.md` by `uom-codegen` (drift-tested like the sources). The public API is pinned by a test against a committed list of exported packages and public types.

**Tech Stack:** Java 21, Maven 3.9, JUnit 5.10.2, `javax.measure:unit-api:2.2`; GitHub Actions for CI; plugins: maven-enforcer, maven-source, maven-javadoc, maven-gpg, `org.sonatype.central:central-publishing-maven-plugin`.

**Spec:** `docs/DESIGN.md` (section 7), `docs/REQUIREMENTS.md` (N7, N8, F13, acceptance criteria 6 and 7), `docs/superpowers/plans/2026-10-12-uom-m6-follow-ups.md`. Branch `m7-release` is stacked on `ng` (= `m6-release` plus the todo list).

## Global Constraints

- **Nothing is published.** No `deploy`, no tag, no signing keys, no secrets, no network access from the build beyond Maven Central dependency resolution. The `release` profile is never active by default and its signing and upload steps are skipped unless explicitly enabled; the workflow added here has no deploy job. The real release (version bump, tag, signing, upload) is the owner's action (owner decision).
- Java baseline 21; Maven multi-module; Apache-2.0; every `.java` file starts with `// SPDX-License-Identifier: Apache-2.0` (generated files: that line plus `// Generated by uom-codegen from data/<files>; do not edit.`).
- Version stays `0.1.0-SNAPSHOT` (owner decision); published artifacts: `uom-parent` (pom), `uom-core`, `uom`; NOT published: `uom-codegen`, `uom-tck`, `uom-examples`.
- Runtime dependency: only `javax.measure:unit-api` 2.2 (named module `java.measure`).
- Generated sources and the generated `docs/UNITS.md` are committed; regenerate with `mvn -q -B -Pgenerate -pl uom-codegen -am process-classes`; the drift test must pass; output deterministic (LF).
- Commit subjects use a conventional prefix (`feat:`, `fix:`, `test:`, `build:`, `docs:`, `ci:`), no emojis, trailer `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`; code comments 1-3 lines; scripts and tests assert exact values.
- The open owner decisions and owner-requested follow-ups in `docs/TODO.md` stay open.

## Decisions for this milestone

- **D1 POM metadata (owner-confirmed).** Parent POM: `name`, `description`, `url` and `scm` (`https://github.com/TinyGearsOrg/tinyunits`, `scm:git:...`; update after the repository rename), `licenses` (Apache-2.0, `https://www.apache.org/licenses/LICENSE-2.0.txt`), `developers` (id `tneidhart`, name Thomas Neidhart, email `thomas.neidhart@gmail.com` from the git configuration), `issueManagement`, `inceptionYear`. Each published module has its own `name` and `description`.
- **D2 Release profile.** `release` (inactive): `maven-source-plugin` (`jar-no-fork`), `maven-javadoc-plugin` (`jar`, doclint all, fail on warnings), `maven-gpg-plugin` (`sign`; skipped when `gpg.skip=true`, which is the default for the verification script), `central-publishing-maven-plugin` (`publishingServerId=central`, `autoPublish=false`, `skipPublishing=true` on `uom-codegen`, `uom-tck`, `uom-examples`). Always on: `maven-enforcer-plugin` (Java 21+, Maven 3.9+, banned duplicate dependency versions), explicit plugin versions (the build warns about the missing `maven-deploy-plugin` version today), `project.build.outputTimestamp` for reproducible jars, jar manifest entries (`Implementation-Title`, `Implementation-Version`, `Implementation-Vendor`), `deploy` skipped for `uom-codegen`, `uom-tck`, `uom-examples`. A manual upload step in the Central Portal remains after `autoPublish=false`.
- **D3 Public API definition (N8).** Public API = the exported packages: `org.tinygears.uom.core`, `org.tinygears.uom.core.parse`, `org.tinygears.uom.core.quantity` (module `org.tinygears.uom.core`), `org.tinygears.uom.quantity` and `org.tinygears.uom.systems` (module `org.tinygears.uom`). `org.tinygears.uom.core.internal` is internal (not exported; its public classes are not API). `docs/API.md` states the policy (semantic versioning from 1.0; what counts as API: public and protected members of public types in exported packages, the generated constant names of the catalogs, the `.units` file syntax, the serialized form after 1.0; what does not: internal packages, test helpers, generator internals, unit symbols of non-catalog units); a test pins the exported packages and the set of public top-level types and public members of each against `docs/api/public-api.txt` (written with `-Duom.writeApi`), so an accidental public member fails the build and a deliberate change is a visible diff.
- **D4 Unit table (N7).** `uom-codegen` generates `docs/UNITS.md`: one section per system, a table of symbol, name, quantity type (or `-`) and the exact factor to the system unit (fraction or decimal as in the offset format, with the offset when present) for every unit of the catalog, plus a short "systems" index. It reads the data files (no generated-module dependency, bootstrap rule). The drift test covers it.
- **D5 Documentation set.** `README.md` (five-minute example, install, links), `docs/CUSTOM-UNITS.md` (the `.units` guide: syntax reference of every directive and the formula grammar including the shift rule, `load`/`with`, errors, caveats; its fenced `units` and `java` snippets are executed by a test), `docs/API.md` (D3), `docs/RELEASING.md` (the release procedure for the owner, the Central Portal namespace and token steps, signing, the checklist), `CHANGELOG.md` (Keep a Changelog, an `Unreleased` section summarising milestones 1 to 6), `SECURITY.md` (serialization advice with the `ObjectInputFilter`, reporting), `CONTRIBUTING.md` (build, regeneration, tests, conventions, the licence-header rule).
- **D6 CI (owner-confirmed: CI workflow only).** `.github/workflows/ci.yml`: on push and pull request; matrix JDK 21 and 25 (Temurin); `mvn -B verify`; the generator drift check (`mvn -B -Pgenerate -pl uom-codegen -am process-classes` then `git diff --exit-code`); `scripts/verify-release.sh` on one JDK; `permissions: contents: read`; no secrets, no deploy. `.github/dependabot.yml` for Maven and GitHub Actions. Pushing the branch starts the workflow on GitHub.

## Review Focus

1. **Central rules.** Every published artifact has the required metadata (name, description, url, licenses, developers, scm), a sources jar and a javadoc jar, a valid POM (no unresolved properties, no `-SNAPSHOT` dependencies other than the project's own), and the not-published modules produce no upload (Tasks 1, 5).
2. **Reproducibility and contents.** Two builds give identical jar bytes; jars contain `module-info.class`, `LICENSE`, the manifest entries and nothing stray (no tests, no data files in `uom`, no `.superpowers`); `jar --describe-module` is right; `jlink` works with the named modules (Task 5).
3. **API pin.** The exported packages and public types match `docs/api/public-api.txt`; `org.tinygears.uom.core.internal` is not exported; no accidental public member (Task 2).
4. **Docs are true.** The snippets of `docs/CUSTOM-UNITS.md` run; the unit table equals the catalogs (drift test, spot checks against the data files); `README.md`, `API.md` and `RELEASING.md` match the code and the commands (Tasks 3, 4, 7).
5. **Consumer view.** A separate project that depends only on `org.tinygears:uom` (installed to a temporary local repository) compiles and runs on the class path and on the module path with JDK 21 and the current JDK (Task 5); the CI workflow is valid, least-privilege and contains no deploy step (Task 6).
