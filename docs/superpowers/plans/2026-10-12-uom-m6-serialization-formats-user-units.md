# uom Milestone 6: Serialization, Locale-Aware Formats and User Units Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Units and quantities survive Java serialization; quantity formats are locale-aware for numbers and can parse exact decimals; every unit, offset units included, has a faithful text form; users can load their own `.units` files at run time and use them in unit parsing, without any global registry.

**Architecture:** Serialization uses the serialization-proxy pattern (proxies call the public factories, so every invariant is re-checked on read). The formula grammar gains a trailing shift (`K+273.15`) that makes offset units formattable. `UomQuantityFormat` becomes an immutable value with `withLocale` and `withDecimals`. A parser overload takes a lookup of already-known units, so a user file can use the built-in symbols; `UomSystemOfUnits.load` turns it into an immutable system and `UomUnitFormat.with` adds it to a new format.

**Tech Stack:** Java 21, Maven, JUnit 5.10.2, `javax.measure:unit-api:2.2`.

**Spec:** `docs/DESIGN.md` (sections 3 to 7), `docs/REQUIREMENTS.md` (F9, F12, F13, F17, F18, F19, acceptance criteria 1, 4, 5), the follow-ups `docs/superpowers/plans/2026-10-12-uom-m3-follow-ups.md`, `2026-10-12-uom-m4-follow-ups.md`, `2026-10-12-uom-m5-follow-ups.md`. Branch `m6-release` is stacked on `ng` (= `m5-systems`); milestone 7 (release engineering) follows and is not part of this plan.

## Decisions for this milestone

- **D1 Serialization (F12).** Serialization proxy pattern for `Factor`, `UomDimension`, `UnitAtom`, the converters and `UomUnit`, and for quantities. Each class that is serialized declares `Serializable`, throws `InvalidObjectException("proxy required")` from `readObject`, returns its proxy from `writeReplace`, and each proxy has an explicit `serialVersionUID = 1L` and rebuilds the object through the public factories in `readResolve` (so normalisation and invariants are re-checked); any violation is an `InvalidObjectException` with a clear message. A unit serializes as its atoms, converter factor and offset, symbol and name (not the converter cache). An alternate-unit atom serializes with its symbol, dimension and defining atoms; on read the dimension must match the definition and a registered symbol must have the identical definition (else `InvalidObjectException`) and resolves to the registered atom, while an unregistered symbol gives an equal but unregistered atom: reading never registers (amended in review: untrusted data must not bind symbols or grow the registry), so reading works in a fresh JVM that has not touched `SI` and a later `alternate(symbol)` with the same definition gives equal units. Proxies write their values unshared with bounded lengths (at most 1000 atoms or conversion steps), so the bytes do not depend on object identity. A quantity serializes as kind (`double` or decimal), value, unit, `Scale`, `MathContext` (decimal) and the standard quantity interface class (`Untyped` for untyped); on read it is created through `ServiceProvider.current().getQuantityFactory(type)` and then re-created with the exact value and context by the existing package-private `with` helper (so digits beyond the context survive); a unit whose dimension differs from the type's, a scale beyond the D9 bound of milestone 4, null fields or an unknown type are `InvalidObjectException`. Systems, formats, services and converter caches are not serializable (not required by F12). The serialized form is pinned by golden byte files in test resources and is not promised stable before 1.0 (documented).
- **D2 Shift syntax (faithful offset form).** A formula may end in `+n` or `-n` (top level only, after the whole expression): `expr+n` is `expr.shift(n)` (a value `v` in the new unit is `v + n` in `expr`), where `n` is a decimal literal or an exact fraction `a|b` (no units, no parentheses). `+` and `-` become delimiters when scanning symbols (a regression test proves no catalog or data symbol contains them and that every string that parsed before still parses identically). `UomUnitFormat.format` of an offset unit with factor `f` and offset `o` in its system unit `S` emits `<f-formula>·S+(o/f)` with the shift as an exact fraction or decimal, after the existing symbol-first rules (label, symbol, catalog symbol); `parse(format(u))` equals `u` for every unit the format can build, offset or not.
- **D3 Locale-aware quantity format (owner-confirmed: numbers only).** `UomQuantityFormat` is immutable with `withLocale(Locale)` and `withGrouping(boolean)` (default `Locale.ROOT`, no grouping, output identical to today's). For a non-ROOT locale the value text is the same shortest representation (`Double.toString` or `BigDecimal.toString`) with its characters mapped through `DecimalFormatSymbols`: digits to the locale's digit set, `.` to the decimal separator, `-` to the minus sign, `E` to the exponent separator; no grouping is emitted. Parsing accepts the locale's digits and ASCII digits, decimal separator, minus sign (and ASCII `-`), exponent separator or `E`; a grouping separator is a `MeasurementParseException` unless `withGrouping(true)`, in which case grouping separators between digits are skipped (never emitted). Unit symbols are not localized. `isLocaleSensitive()` is true for a non-ROOT locale. `UomFormatService` is unchanged (it keeps the ROOT format named `default`).
- **D4 Decimal-preserving parse (follow-up of D12 of milestone 4).** `UomQuantityFormat.withDecimals(MathContext mc)` returns a format whose `parse` yields decimal quantities (typed through the standard factories, `UntypedDecimalQuantity` otherwise) carrying exactly the digits of the text and the context `mc`; `format` is unchanged. The default format keeps parsing to `double`. For a decimal quantity `q` of any type, `withDecimals(q.mathContext()).parse(format(q))` equals `q` in every locale of D3 (including trailing zeros: `1.50 km` keeps scale 2).
- **D5 User units (owner-confirmed: explicit, no global state).** `DefinitionParser.parse(source, reader, resolver, known)` takes a `Function<String, UomUnit<?>> known`; symbols a file does not define resolve through it, and a file defining a symbol that `known` resolves is an error `symbol 'm' is already defined` with file and line. `UomSystemOfUnits.load(String name, Reader reader, DefinitionParser.Resolver resolver)` and `load(Path file)` (name from `@system`, else the file name without extension; `@include` resolved relative to the file's directory) return an immutable system of the file's definitions: constants are `Unit<?>` (callers narrow with `asType`), `@preferred Type symbol` names one of the 33 standard types by simple name (anything else is an error with file and line), `@prefixed` works, `@extends`/`@include` only reach user files (no built-in resources are shipped). Unlisted types fall back to SI's preferred unit (as D4 of milestone 5), so `to(userSystem)` works. The built-in symbols (exact catalog symbols and metric prefixes, not labels) are the `known` lookup, exposed as `UomUnitFormat.resolve(String symbol)` returning `Optional<UomUnit<?>>`. `UomUnitFormat.with(UomSystemOfUnits... systems)` returns a new format over the existing systems followed by the given ones, labels copied; a symbol of a given system that equals a symbol of another system with a different unit is an `IllegalArgumentException` naming both (equal units are fine). Nothing is registered globally; two formats can hold different systems with the same symbol. Alternate units (`~` lines) in user files register permanently in the JVM-wide registry (existing, documented behaviour).
- **D6 Out of this milestone.** Release engineering (POM metadata, sources and javadoc jars, signing profile, CI on JDK 21 and the current JDK, the custom-unit guide and unit table of N7, versioning policy of N8, repository rename) is milestone 7; publishing stays the owner's action. Localized unit names, user-defined quantity types and serialization of systems are out of scope.

## Review Focus

1. **Deserialization safety.** Forged streams (invalid `Factor`, mismatched dimension, absurd scale, null fields, an alternate-unit symbol bound to a different definition, a huge `BigInteger`) end in `InvalidObjectException`, never a corrupt object or a hang; read works in a fresh JVM (Tasks 1, 2).
2. **Round trips.** Every one of the 298 catalog units and every type in {double, decimal} x {ABSOLUTE, RELATIVE}, decimal contexts and untyped quantities survive serialization with `equals`; golden bytes fail on an accidental change of the form (Tasks 1, 2).
3. **Grammar regression.** Adding `+` and `-` as delimiters changes no existing parse: every symbol, prefixed form and formula that parsed before parses to the same unit; `1e+5`, `K+273.15`, `°C+1`, `m+1` are unambiguous; every offset unit formats and parses back (Tasks 3, 4).
4. **Locales.** Format and parse round trips in every `Locale.getAvailableLocales()` entry for double and decimal values (negative values, exponents, `0.5`, huge and tiny magnitudes), ROOT output byte-identical to milestone 5, grouping rejected by default, locale digits (Arabic, Devanagari) handled (Tasks 5, 6).
5. **User units.** Symbol conflicts, redefinition, include cycles, error positions, no global state (two formats with different systems using the same symbol), preferred layering, alternate-unit permanence documented (Task 7).
